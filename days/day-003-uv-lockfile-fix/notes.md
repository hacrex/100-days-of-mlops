# Day 3 — Implementation Notes

## What I Did

Replaced pip with uv for package management and set up the lockfile workflow.

## Speed Comparison

| Operation | pip | uv |
|-----------|-----|----|
| Install numpy + pandas + scikit-learn | ~45s | ~3s |
| Resolve dependencies | ~20s | ~1s |
| Create venv | ~2s | ~0.3s |

## Lockfile Workflow

### Step 1: Create requirements.in (direct dependencies only)

```
numpy>=1.26
pandas>=2.0
scikit-learn>=1.4
```

### Step 2: Compile to a pinned lockfile

```bash
uv pip compile requirements.in -o requirements.txt
```

Output (`requirements.txt`):
```
# This file was autogenerated by uv via the following command:
#    uv pip compile requirements.in -o requirements.txt
joblib==1.3.2
    # via scikit-learn
numpy==1.26.4
    # via
    #   pandas
    #   scikit-learn
    #   scipy
pandas==2.2.1
    # via -r requirements.in
...
```

### Step 3: Sync the environment

```bash
uv pip sync requirements.txt
```

This installs exactly what's in the lockfile and removes anything else.

## The "Lockfile Fix" Problem

The day title references a common issue: when you have a `requirements.txt` that was generated on one platform (e.g., macOS) and try to install it on another (e.g., Linux), some packages fail because they include platform-specific wheels.

`uv pip compile` handles this with `--platform` and `--python-version` flags:

```bash
# Generate a lockfile for Linux Python 3.11
uv pip compile requirements.in \
  --platform linux \
  --python-version 3.11 \
  -o requirements-linux.txt
```

## Observations

- uv's error messages are much clearer than pip's when there are conflicts
- The `# via` comments in the compiled lockfile are extremely helpful for understanding why a package is included
- uv is a drop-in replacement for pip in most cases — `uv pip install` works exactly like `pip install`
